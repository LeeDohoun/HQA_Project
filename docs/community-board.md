# 게시판 운영과 검증

## 2026-10-11 팀 브랜치 통합 검증

`feat/team-integration`의 최신 내용에 게시판·프로필 변경사항을 통합했다. 공통 API에 게시판/프로필 클라이언트와 닉네임 매핑을 복구하고, 기존 요청 제한 시간·취소·오류 메시지를 유지하면서 변경 요청에 CSRF 토큰을 전달한다. 204/205 빈 응답도 처리한다. 누락된 요청 인자는 400, 지원하지 않는 HTTP 메서드는 405와 Allow 헤더로 응답한다. 대시보드는 `(workspace)`로 이동해 중복 경로를 제거했으며 메인 화면의 게시판 메뉴도 복구했다. Next.js 버전과 lock 파일을 일치시켰다.

검증은 운영 데이터와 분리한 PostgreSQL/Redis 및 테스트 계정으로 수행했다.

- 프런트엔드: `npm ci` 후 테스트 34개 통과, 프로덕션 빌드와 타입 검사 통과.
- 백엔드: PostgreSQL 통합 테스트를 포함한 214개 통과. 별도로 Java 주문 수명주기와 Python SignalMonitor 시뮬레이션 1개도 통과했으며 내부 확인 항목은 167/167이다.
- 실제 HTTP 흐름: 87개 확인 통과. 세션·CSRF·설문·닉네임·게시글 수정 권한·댓글 커서·중복 추천·포인트 회수·비공개 문의·관리자 대상 글 삭제·종목 필터·워치리스트·미설정 계좌 차단·로그아웃을 확인했다.
- Chrome: 13개 시나리오 통과, 페이지 실행 오류 0건. 메인 게시판 메뉴·비로그인 접근·로그인·자동매매 상태·탭 새로고침·설문 자산·닉네임·게시글 작성/수정/삭제·댓글·기존 자산 주소 이동·320/390px 메뉴와 문서 너비·로그아웃·관리자 문의 메뉴를 확인했다.
- Python 전체 테스트: Linux 테스트 컨테이너에서 1,441개 통과, 8개 생략. 읽기 전용 경로의 감사 DB 쓰기 오류로 실패한 1개는 `/tmp` 감사 DB 경로를 지정한 재검증에서 통과했다.

실제 KIS 주문과 유료 모델 호출은 수행하지 않았다. 외부 서비스 연동은 자동 테스트의 모의 응답과 모의 브로커 범위에서 검증했으며, 실계좌/실제 모델의 응답이나 운영 환경 전체 기능을 보증하는 결과는 아니다. 임시 테스트 서버와 컨테이너는 검증 후 정리한다.

게시판 주소는 `/community`다. 메인 화면·대시보드·투자 성향 초기 설정 화면·공통 헤더의 `게시판` 드롭다운에서 자유게시판·종목토론방·문의를 선택한다. 문의 항목은 관리자에게 `문의 관리`, 일반 사용자에게 `내 문의`로 표시한다. 게시판 선택은 이 드롭다운 하나로 통일하며, 목록 제목에는 선택한 게시판 이름을 표시한다. 투자 성향 설문을 완료하기 전에도 게시판을 이용할 수 있으며, 비로그인 상태에서는 로그인 안내를 표시한다.

대시보드와 게시판은 `(workspace)` 공통 레이아웃을 사용한다. 목록·상세·글쓰기·수정·문의 관리로 이동해도 홈·워치리스트·AI 분석·거래 내역·마이 페이지·게시판 메뉴와 로그인 계정 상태를 유지하고 본문을 교체한다. 글쓰기·목록·수정 버튼은 본문 제목 옆에 표시한다. 대시보드 탭은 `/dashboard?tab=watchlist`처럼 주소에 기록하므로 게시판에서 돌아오거나 새로고침·뒤로가기를 해도 선택한 탭을 복원한다. 공개 주소와 게시판의 목록 복귀 계약은 기존과 같다.

## 포인트·추천·마이 페이지

상단의 `마이 페이지`는 `/mypage`로 연결한다. 내 자산, 닉네임 변경, 게시판별 포인트·레벨·칭호, 최근 포인트 이력을 조회한다. 예전 `/dashboard?tab=assets` 주소도 마이 페이지로 이동한다. 계좌를 연결하면 KIS 잔고를, 연결 전에는 설문에 입력한 자산을 표시한다.

자유게시판과 종목토론방은 글 작성에 10P, 댓글 작성에 2P, 추천을 받은 작성자에게 5P를 지급한다. 두 게시판의 포인트는 각각 집계하며 문의 작성·댓글에는 지급하지 않는다. 기존의 미삭제 공개 글·댓글에도 V14 마이그레이션에서 같은 기준의 초기 포인트를 지급한다.

| 레벨 | 자유게시판 기준 | 자유게시판 칭호 | 종목토론방 기준 | 종목토론방 칭호 |
| --- | ---: | --- | ---: | --- |
| 1 | 0P | 새싹 | 0P | 시장 관찰자 |
| 2 | 50P | 이야기꾼 | 100P | 종목 탐험가 |
| 3 | 150P | 소통지기 | 300P | 투자 연구원 |
| 4 | 300P | 인기 논객 | 600P | 분석 전문가 |
| 5 | 600P | 커뮤니티 리더 | 1,200P | 시장 전략가 |
| 6 | 1,000P | 소통의 전설 | 2,000P | 투자 현자 |

다른 회원의 공개 글만 추천할 수 있다. `POST /api/v1/community/posts/{id}/recommendations`는 세션 사용자로 추천하며 `(post_id, user_id)` DB 고유 제약과 부모 글 잠금으로 중복·동시 추천을 차단한다. 같은 사람이 다시 요청하면 409다. 추천 취소 API는 없고 추천 완료 버튼을 비활성화한다. 추천 기록, 글의 추천 수, 작성자의 포인트 지급은 같은 트랜잭션에서 반영한다.

`community_point_events`는 지급 원장이다. 각 글·댓글·추천당 지급 이력을 하나만 허용하고, 보유 포인트는 회수되지 않은 원장의 합으로 계산하므로 동시에 지급해도 덮어쓰기가 없다. 댓글 삭제는 그 댓글의 포인트를 회수한다. 글 삭제는 해당 글과 댓글·추천에서 지급된 포인트를 모두 회수하되 추천 기록은 유지한다. 레벨과 칭호는 현재 포인트에 맞춰 자동 재계산한다. 삭제 후에도 지급·회수 이력을 마이 페이지에서 확인할 수 있다.

`GET /api/v1/profile`과 `PUT /api/v1/profile/nickname`은 현재 세션 사용자의 정보만 다룬다. 닉네임은 기본적으로 아이디를 사용하며 변경은 2~30자, 문자·숫자·공백·`.`·`_`·`-`로 제한한다. 중복 닉네임은 DB 고유 제약으로 막는다. 글 목록·상세·댓글에는 현재 닉네임과 해당 게시판 칭호를 표시하며, 작성자별 포인트는 목록 단위로 묶어 조회한다.

포인트 기능 검증: 백엔드 전체 174개 테스트(별도 PostgreSQL 통합 검사 24개 포함), 마지막 추천 요청·CSRF 검사 22개, 프런트엔드 27개 테스트와 TypeScript 검사를 통과했다. 실제 Chrome에서 마이 페이지, 닉네임 변경, 추천 완료 상태, 모바일 320/390px, 비로그인 접근을 포함한 7개 시나리오를 검증했다. 개발 DB의 추천·포인트 무결성 8개 항목도 모두 0건이었다. 포인트 검사는 다음 읽기 전용 명령으로 반복한다.

```powershell
Get-Content -Raw backend/scripts/audit-community-points.sql |
  docker exec -i hqa-postgres psql -X -v ON_ERROR_STOP=1 -U hqa -d hqa
```

게시판은 세션 인증을 사용한다. 자유·종목 게시글은 로그인한 사용자에게 공개하고, 문의는 작성자와 관리자에게만 공개한다. 수정은 작성자만 할 수 있고, 댓글이 3개 이상이면 일반 사용자의 글 삭제 대신 관리자에게 삭제 요청을 보내야 한다. 관리자는 문의 답변을 저장하면서 연결된 대상 글을 삭제할 수 있다.

## 데이터 계약

- Flyway V11은 게시판 테이블, V12는 댓글 커서 조회 인덱스, V13은 게시판 종류와 삭제 정보의 무결성 제약을 적용한다. 이미 적용된 마이그레이션은 수정하지 않는다.
- 댓글 생성·삭제와 게시글 삭제는 부모 게시글을 먼저 잠근다. 활성 댓글 수와 `comment_count`는 같은 트랜잭션에서 변경한다.
- 게시글은 `created_at DESC, id DESC`, 댓글은 `created_at ASC, id ASC`로 정렬한다.
- 게시글·댓글 생성/수정 시간은 PostgreSQL의 마이크로초 정밀도로 생성한다. 수정 응답과 DB 재조회 시간은 정확히 일치한다.
- 상세 조회의 초기 댓글은 20개다. 추가 조회는 댓글 ID 커서를 사용하며, 이미 삭제한 댓글도 해당 글의 커서로 사용할 수 있다. 다른 글의 커서는 거부한다.
- `comments/visible?ids=...`는 현재 화면에 표시한 댓글을 재확인하는 용도다. 최대 50개 ID를 받으며 다른 글의 댓글과 삭제한 댓글은 반환하지 않는다. 문의 열람 권한을 먼저 확인한다.
- 목록의 게시판·종목 필터·페이지는 URL에 유지한다. `returnTo`는 `/community`의 정규화된 목록 주소만 허용한다.

## 세션과 CSRF

읽기 요청은 CSRF 토큰 없이 가능하다. `/api/v1/*`의 POST·PUT·PATCH·DELETE 요청은 세션에 연결된 토큰이 필요하다. 회원가입·로그인·로그아웃에도 적용한다.

`/api/v1/*` 응답은 성공·실패 모두 `Cache-Control: no-store`를 보낸다. 사용자 정보·비공개 문의·사용자별 권한 응답을 저장하지 않는다.

1. `GET /api/v1/auth/csrf`로 마스킹된 토큰을 받는다. 응답은 `Cache-Control: no-store`다.
2. 같은 쿠키 세션으로 변경 요청을 보내고 `X-CSRF-Token` 헤더에 토큰을 넣는다.
3. 로그인·회원가입 성공 시 세션 ID를 교체하고 이전 CSRF 토큰을 폐기한다. 이후 변경 요청에는 새 토큰을 조회한다.

프런트엔드의 공통 `api()`는 변경 요청 직전에 새 토큰을 조회한다. 토큰 조회 실패 시 변경 요청을 보내지 않으며, 실패한 변경 요청을 자동으로 재실행하지 않는다. 읽기 요청에는 추가 토큰 조회가 없다.

`/api/v1/internal/*`는 서버 간 호출이므로 CSRF 대상에서 제외한다. 기존 `X-HQA-Internal-Token` 검증은 계속 적용한다. 일반 API에 내부 토큰 헤더를 넣어도 CSRF 검사를 우회할 수 없다.

비활성 계정은 기존 세션으로도 요청할 수 없다. 관리자 권한은 요청마다 DB에서 확인하므로 계정의 역할을 변경하면 기존 세션에도 즉시 반영된다.

## 반복 검증

저장소 루트에서 실행한다. 백엔드 스크립트는 별도의 PostgreSQL 16 컨테이너를 만들고 전체 테스트 후 자신이 만든 컨테이너만 삭제한다. 개발 DB를 테스트 DB로 사용하지 않는다.

```powershell
powershell -ExecutionPolicy Bypass -File backend/scripts/test-community-integrity.ps1
# 의존성 다운로드가 끝난 환경에서는 -Offline 사용 가능
cd frontend
npm ci
npm test
npm run build
npm audit
```

실행 중인 개발 DB의 읽기 전용 무결성 검사는 다음과 같다. 9개 항목의 `violations`가 모두 0이어야 한다.

```powershell
Get-Content -Raw backend/src/test/resources/community-integrity-audit.sql |
  docker exec -i hqa-postgres psql -X -v ON_ERROR_STOP=1 -U hqa -d hqa
```

실제 브라우저 검증은 작성자·다른 사용자·관리자의 별도 세션으로 진행한다. 작성·수정·삭제, 댓글 더 보기와 외부 삭제 반영, 비공개 문의, 관리자 답변과 대상 글 삭제, 목록 새로고침·뒤로 가기·마지막 페이지 삭제를 확인한다. 검증용 데이터는 기존 계정·게시글과 분리하고, 정리 전 다른 사용자가 작성한 댓글이나 문의가 연결되지 않았는지 확인한다.

2026-10-10 검증 결과: 백엔드 163개(별도 PostgreSQL 통합 검사 포함), 프런트엔드 27개 테스트와 프로덕션 빌드가 통과했다. 실행 중인 개발 서버와 실제 Chrome에서 12개 시나리오를 검증했고, 로그인·회원가입 세션 교체, 이전 세션 무효화, CSRF 누락·다른 세션 토큰·경로 정규화·허용되지 않은 출처 차단, 계정 비활성화와 관리자 역할 회수도 확인했다. Flyway V13 적용과 OpenAPI/health 정상 응답을 확인했다. 임시 계정·글·댓글은 모두 정리했으며 기존 사용자 3명·글 6개·댓글 6개를 유지했고, 읽기 전용 무결성 검사 9개 항목이 모두 0건이었다.

| [CVE-2026-47884](https://spring.io/security/cve-2026-47884/) | `XsltView`와 암시적 뷰 이름을 사용하는 광범위 매핑 | XSLT 뷰 구현 없음, API는 JSON 컨트롤러 사용 |

위 사용 조건이 없다는 것은 코드 검토에 따른 판단이며, 백엔드 취약점 검사 결과를 0건이라고 표시하지 않는다. 해당 기능을 추가하기 전에 재검사한다.

[Spring Boot 3.5의 공개 지원은 종료됐다](https://spring.io/blog/2026/06/25/spring-boot-3-5-16-available-now/). 배포 전 후속 작업은 지원 중인 Boot 4 계열 전환이다. Jackson JSON 계약, Hibernate 엔티티·조회, Flyway 자동 구성, springdoc 호환성, 내부 API와 분석·주문 클라이언트까지 함께 검증해야 한다. 이 전환은 게시판 수정 외의 서비스에도 영향을 준다.
